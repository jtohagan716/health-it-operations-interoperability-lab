# OpenEMR MariaDB Patient MRN Search Index Study

## Executive summary

This study evaluated whether OpenEMR patient searches by medical record
number (MRN) could benefit from a non-unique MariaDB index beginning with
`patient_data.pubpid`.

The tested OpenEMR environment already contained indexes supporting patient
identifier, UUID, name, date of birth, and internal identifier access. It did
not contain an index whose leading column was `pubpid`.

At a controlled scale of 50,000 synthetic patients, an MRN-prefix search
without the candidate index examined 50,000 rows and produced a median
execution time of approximately 198 milliseconds for a successful search.
With a non-unique `idx_patient_pubpid (pubpid)` index, the same workload
examined approximately two rows and produced a median execution time of
approximately 0.42 milliseconds.

The candidate index added approximately 48 bytes of index storage per patient.
Paired write testing measured median incremental costs of approximately
0.034 milliseconds per inserted patient and 0.017 milliseconds per MRN update.

These results support further OpenEMR maintainer review of a non-unique
`pubpid` index. They do not establish production-wide performance or justify
an unreviewed schema change across all supported OpenEMR installations.

## Scope

The investigation was deliberately limited to:

- MariaDB used by the local OpenEMR environment;
- the OpenEMR patient finder workflow;
- MRN-prefix searches involving `patient_data.pubpid`;
- deterministic synthetic patient records;
- read-plan, read-latency, storage, insert, and MRN-update effects;
- reversible testing that did not retain an index on the live OpenEMR table.

The study did not evaluate PostgreSQL changes, first-name-only searches,
general-purpose OpenEMR tuning, or unrelated clinical workflows.

## Environment

| Component | Tested configuration |
|---|---|

| Host | Windows 11 with Docker Desktop |
| Live patient population | 101 deterministic synthetic patients |
| Isolated test scales | 1,000, 10,000, and 50,000 patients |
| Instrumentation | MariaDB Performance Schema and execution plans |
| UI validation | Playwright patient-chart workflow |

Performance Schema was enabled through a Compose override rather than by
changing the base OpenEMR environment permanently.

## Existing schema state

The tested fresh lab schema contained the following `patient_data` indexes:

| Index | Leading column or columns | Purpose observed |
|---|---|---|
| `pid` | `pid` | Unique patient identifier |
| `uuid` | `uuid` | Unique UUID access |
| `idx_patient_name` | `lname, fname` | Patient-name search |
| `idx_patient_dob` | `DOB` | Date-of-birth access |
| `id` | `id` | Internal identifier access |

No index in the tested schema began with `pubpid`.

This does not mean that OpenEMR has no indexes. It means that this tested
schema did not have an index capable of directly supporting the observed
MRN-prefix predicate.

## Query discovery

The investigation began by executing the real Playwright patient-chart
workflow and observing database activity generated by OpenEMR.

The captured patient finder used prepared SQL with bind parameters. A
representative shape was:

```sql
SELECT *
FROM patient_data
WHERE 1
  AND fname LIKE ?
  AND lname LIKE ?
ORDER BY lname ASC, fname ASC
LIMIT 0, 100;
```

The execution supplied values separately from the SQL text. This finding is
important because it did not reproduce the literal-SQL behavior previously
encountered in other healthcare systems. Bind-variable remediation was
therefore not indicated for this workflow.

The existing composite name index supported the full-name search efficiently.
The investigation then compared other clinically relevant search shapes.

## Search-plan matrix

| Search shape | Observed access |
|---|---|
| Last-name prefix | Range access through `idx_patient_name` |
| Full name | Range access through `idx_patient_name` |
| Last name plus DOB | Name-index range with remaining filtering |
| Full name plus DOB | Composite name-index range with remaining filtering |
| MRN prefix | Full scan of `idx_patient_name`, followed by filtering |

The optimizer used `idx_patient_name` for the unindexed MRN query primarily
because it could help return rows in the requested name order. It still had to
examine the patient population to find matching `pubpid` values.

First-name-only search was intentionally excluded. The intended clinical
workflow should not encourage an insufficiently constrained first-name-only
patient lookup. That case is better treated as a future negative workflow or
usability-control test than as an indexing target.

## Candidate index

The evaluated candidate was:

```sql
CREATE INDEX idx_patient_pubpid
    ON patient_data (pubpid);
```

The candidate was non-unique.

The synthetic data contained unique MRNs, but the study did not assume that
all OpenEMR installations enforce global pubpid uniqueness. A unique index
would introduce a data-integrity rule in addition to a performance change and
would require separate product and migration analysis.

## Experimental controls

The study used the following controls:

- a separate `openemr_performance_lab` database;
- fixture tables created from the live `patient_data` structure;
- deterministic synthetic identifiers and MRNs;
- exact row-count and distinct-MRN validation;
- preservation checks against the live 101-patient OpenEMR table;
- warm-up executions before measured read samples;
- 100 measured executions per read scenario;
- hit and miss scenarios;
- index creation followed by explicit cleanup verification;
- paired write comparisons using equivalent indexed and unindexed tables;
- alternating execution order between write variants;
- transactional rollback for MRN-update measurements; and
- SHA-256 evidence hashes.

Alternating write order distributed first-run cache effects, dirty-page
activity, checkpoints, and host scheduling effects across both variants. It
did not remove all environmental noise, so paired medians and ranges are
reported rather than a single unqualified percentage.

## Execution-plan change

Without the candidate index, MariaDB reported an index scan using
`idx_patient_name` and applied the MRN predicate as a filter.

With the candidate index, MariaDB reported range access using
`idx_patient_pubpid`, with an estimated single matching row.

The indexed plan retained a filesort for name ordering. For selective MRN
searches, the sort operated on approximately one matching row and was
negligible compared with scanning the patient population.

## Storage and index construction

At the 50,000-patient scale:

- candidate index creation took approximately 652 milliseconds in one
  environment-specific observation;
- index storage increased by 2,637,824 bytes;
- the increase was approximately 48 bytes per patient; and
- combined table and index storage increased by approximately 12.9%.

Index-creation times were not monotonic across scales because they were single
observations affected by cache and host conditions. They are retained as
operational context rather than treated as benchmark conclusions.

## Insert overhead

Two equivalent 50,000-row tables were created. Only one contained the
candidate MRN index. Ten paired batches of 500 patients were inserted into
both tables, with execution order alternating by batch.

| Measure | Result |
|---|---:|
| Paired batches | 10 |
| Rows inserted per variant | 5,000 |
| Median additional time per 500 indexed inserts | 17.052 ms |
| Average additional time per 500 indexed inserts | 23.584 ms |
| Median additional time per patient | 0.034 ms |
| Average additional time per patient | 0.047 ms |
| Minimum paired difference | -21.324 ms |
| Maximum paired difference | 122.589 ms |

The indexed variant was not slower in every pair, demonstrating host and
storage variability. The central result is a modest absolute insert cost,
not a guaranteed fixed percentage penalty.

## MRN-update overhead

Ten paired 500-row MRN updates were executed against the indexed and
unindexed fixture tables. Each update was performed inside a transaction and
rolled back immediately after timing.

| Measure | Result |
|---|---:|
| Paired batches | 10 |
| Rows updated per batch | 500 |
| Median additional time per 500 indexed updates | 8.300 ms |
| Average additional time per 500 indexed updates | 8.830 ms |
| Median additional time per patient | 0.0166 ms |
| Average additional time per patient | 0.0177 ms |
| Minimum paired difference | -62.271 ms |
| Maximum paired difference | 78.611 ms |
| Pairs in which the indexed update was slower | 8 of 10 |

Rollback validation confirmed zero retained update markers, 55,000 rows in
each write fixture, and 101 patients in live OpenEMR.

## Operational interruption

During final evidence capture, the MariaDB container was temporarily
unavailable through its local socket.

Investigation found:

- the container had undergone a stop/start cycle;
- MariaDB performed Aria and InnoDB recovery;
- the server subsequently reported that it was ready for connections;
- Docker reported the container healthy;
- free host physical memory had fallen to approximately 0.21 GB;
- free virtual memory had fallen to approximately 0.50 GB; and
- live and isolated fixture counts remained correct after recovery.

Unrelated Mirth and Orthanc services were stopped to reduce resource pressure.
No performance measurements were repeated after the database restart because
the changed buffer-cache state would have mixed incomparable conditions into
the completed dataset.

This event is retained as part of the engineering record rather than omitted
from the report.

## Interpretation

The measured read benefit increased with patient population because the
unindexed query examined the population while the indexed query remained
selective.

At 50,000 patients, the difference was large enough to be operationally
meaningful. The associated storage cost and measured write costs were small
in absolute terms in this environment.

The study therefore supports the following bounded conclusion:

> A non-unique index beginning with `patient_data.pubpid` is a credible
> OpenEMR MariaDB optimization candidate for selective MRN-prefix patient
> searches. Maintainer review and validation against supported versions,
> representative production distributions, upgrade behavior, and concurrent
> workloads should precede an upstream schema change.

## Limitations

- Testing used deterministic synthetic data rather than production PHI.
- The host had limited memory and also ran other healthcare lab services.
- The indexed and unindexed variants were tested locally, not under
  multi-user production concurrency.
- MariaDB 11.8.8 was tested; other supported versions may choose different
  plans.
- The study focused on a selective MRN-prefix query shape.
- The UI workflow includes application, network, iframe, and rendering time
  that cannot be attributed solely to the database query.
- Index creation was measured with single observations and is not presented
  as a stable deployment-duration estimate.
- The study did not assess every OpenEMR query involving `pubpid`.
- The synthetic fixture had unique MRNs, but uniqueness was not proposed as
  a schema requirement.

## Recommended next actions

1. Convert the experiment into a repeatable, fail-closed benchmark harness.
2. Add automated checks proving the harness targets only the isolated
   performance database.
3. Validate supported MariaDB/MySQL versions identified by OpenEMR
   maintainers.
4. Evaluate representative duplicate and nonuniform MRN distributions.
5. Add controlled concurrency testing.
6. Revalidate the real Playwright patient-search workflow with the candidate
   index temporarily applied and then removed.
7. Share a concise OpenEMR community note linking to the complete evidence
   and inviting maintainer review.
8. Do not submit a permanent schema migration until compatibility and upgrade
   behavior have been reviewed.

what remains unknown, and how it could be evaluated responsibly for OpenEMR.
